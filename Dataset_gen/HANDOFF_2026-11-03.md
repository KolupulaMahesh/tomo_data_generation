## 3. What it does

The Blender packing scene's machinery is rebuilt in Python (curves, hierarchy, constraints, legacy IK, the data team's Synthesizer). So Isaac computes the motion the way Blender does, moves objects, and renders.

```
.blend  (read only)
  -> blender_scripts/export_rig.py, export_scene_usd.py   -> blender_export/<scene>/
  -> scenes/<scene>.yaml   (what the .blend doesn't say)
  -> make_motion.py --seed N      random offset inside the .blend's Synthesizer ranges, motion re-solved, random look
  -> robot_limits/check_motion.py report only, limits.json
  -> render_episode.py            Isaac, colour + depth, live head camera lens
  -> pack_episode.py              the training's fs_NNN format
  -> datasets/<scene>_<date>/ + task.yaml
```

```bash
cd ~/Desktop/tomo_vla_trainer-main/Dataset_gen/blender_to_isaac
bash generate.sh iPhone_Packing_local 50                # 50 whole episodes, seeds 0-49
bash generate.sh iPhone_Packing_local 50 0 505 --bars   # up to the closed lid, live camera's black bars painted in
bash dataset_generator.sh                               # its own window
env/bin/python check_synth.py iPhone_Packing_local      # prove the Synthesizer against Blender
```

About 5 min per whole episode on the laptop (RTX 5050). The same seed gives the same episode. Finished episodes are kept if you stop.

**Needs:** Isaac Sim at `~/isaacsim`, this folder's `env/`. For a re-export: Blender 5.2.2 at `~/blender/blender-5.2.2-linux-x64/` with the `MMRT_Blender_Utilities` add-on.

## 6. What we found

**Only the phone varies.**
- 870 of 1116 frames (78%) have identical motion in every episode: READY, and everything from frame 291 on (spread 0.000°, both datasets).
- The model can only learn to follow what varies.

**The hand does follow a moved object in the data.**
- Cup vs phone when the vacuum turns on: 0.00 mm spread (224 episodes), 0.03 mm (10 episodes).
- Hand vs phone yaw: 90.000° across 10 episodes, spread 0.0004°.
- So a `.blend` with its Synthesizer panel filled in already gives a varied dataset. Use one entry per object: the add-on refuses duplicates, and our `synth.py` keeps the last one.

**The dataset's own fingers go into the box (11-03).** Blender has no collisions. After the box is in the jig (box x 26.4-30.0 cm, top 17.43 cm):

| Frames | What's happening | Depth inside the box, upper estimate |
|---|---|---|
| 808-816 | Hands come in beside the box | Up to 1.7 cm |
| 832-872 | Both hands at the box | 0.6-1.6 cm |
| 912-1004 | Left hand stays on the box during tape | 1.6-1.8 cm, mostly left thumb |

- Using only link centres, the overlap is 0.4-0.7 cm. The true depth is between.
- Sampled frames only, using `check_objects_hlc`'s meshes on fs_000 of the oct27 dataset.
- A real box can't be passed through, so real fingers push on it. This is the likely source of the "press" Praveen saw. Praveen is testing by playing the dataset on the robot.
- Height readings can't fix this: hand and box move together. It has to be fixed in the motion.

**Real cell vs Blender heights (11-03).** Same raw-depth code on renders and 3 real pictures.

| Height (cm) | Blender | Real | Real vs Blender |
|---|---|---|---|
| Table | -0.01, flat, at the robot base height | -0.24, -0.56, -0.69 near the phone | About 0.5 lower |
| Tray rim above table | About 6.9 | About 6.8 | Matches |
| Phone top above table | About 2.9 | About 3.6 | Real box about 0.6 thicker |

- Not exact: the fitted tilt changes run to run, up to 0.88°.
- Independent support: the real grab that works is 0.40 cm below the dataset's hand (20.8 vs 21.16 cm).
- A lower table doesn't explain pressing: the hand ends up further above it, not closer.
- **Real jig height has never been measured.** The real box in the jig read 0.8-1.9 cm nearer the robot than W2 expects.

**Ruler check still needed:**
- Fingertip gap to the table at fs_000 frame 155: `RF_link_2endeff` 5.83, `_3` 5.55, `_4` 5.81, `_5` 5.94 cm.
- Phone box thickness: Blender about 2.9 cm.

**Speed.** Played at 30 fps, the fastest head or arm joint reaches 584°/s at frame 655 (median 58°/s). The robot allows 52°/s. The robot brain paces its commands, so Praveen's view is that speed isn't the problem as long as correct joints are sent. **Any replay of the dataset on the robot must be slowed down.**

**Timing bug (fixed in this generator).** Replicator `step()` plays the timeline on before each capture. `render_episode.py` passes `delta_time=0.0`. The frozen teammate generator doesn't, so in `fullsequencedatasetoct27` the carton and tape are a fraction of a frame ahead of the robot and phone.

**Vacuum labels.** New data takes them from the `.blend` markers' IO byte. They differ from the old `suction` at frames 594-607, where the markers keep the right vacuum on.

**Not explained.** Full render vs the frozen generator: depth differs on 0.018% of pixels.
